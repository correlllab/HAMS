================================================================================
FABEL SILVER BULLETS — RoboCasa H1-2 plant vs mjpc twin sim-to-sim stand gap
================================================================================
Mission: make the shared MJPC stand controller balance indefinitely, unassisted,
on the RoboCasa plant (post-release z >= 0.95 sustained >= 300 sim-s, strap ~0 N,
reproducible on >= 3 episodes). Baseline: 5/5 falls in 16.5-141.7 sim-s with the
band bearing 570-690 N (audit section 13, measured 2026-07-06).

Phase-A ground truth that reshapes the audit's ranking (verified by 4 parallel
code readers over the twin clone, mujoco_mpc deploy core, robosuite assembly,
and the safety layer):

  G1. The section-13 soak was DOUBLY broken on dt: the plant ran 0.002 while
      mjpc_fullbody.yaml already assumed 0.005 (twin_dt AND estimator tick_dt).
      deploy_common.cc:832-846 clocks the whole bring-up + the base-velocity
      finite-diff off lowstate tick * twin_dt, so the choreography ran 2.5x too
      fast and the planner saw base velocities scaled to ~0.4x. Not just a
      physics-parity delta - a broken test harness.
  G2. gravity_ff is a PER-PLANT deploy parameter by the fork's own flag doc
      (h12_lower_body_controller.cc + h12_control_node.cc, identical text):
      "REAL robot: 0.85. TWIN bench: 0 (the twin's gravcomp over-lightens the
      legs at 0.85 -> knee-strut collapse)". The bench yaml runs 0.85 against a
      MuJoCo plant; only 0.85-vs-1.0 was ever bracketed (H2/H3), never 0. The
      observed RoboCasa failure = vertical knee-buckle sag.
  G3. The twin plant's <default> joint class REACHES ITS FREE BASE JOINT:
      dof_damping[0:6]=10, dof_armature[0:6]=0.1 (only frictionloss zeroed,
      h1_2_handless_magpie.xml:12,51-56). The PLANNER model has the same
      (h1_2_modified_magpie.xml:114-116, childclass h1_2, default damping 10 /
      armature 0.1; free joint carries no override). The RoboCasa plant's free
      joint is 0/0/0 (verified compiled). Twin AND planner balance a base with
      a sky-hook damper; the local plant does not have it. Missed by the audit.
  G4. --real-hands closes only HALF the hand-mass gap: robosuite base.xml
      inertiagrouprange="0 0" drops the visual-mesh copies, so each assembled
      gripper is 0.2528 kg vs the twin/planner 0.506 kg lump; the 0.67 kg
      back_equipment box is absent entirely. Total ~1.18 kg upper-body deficit
      even at full flags (local 67.49 kg vs twin 68.67 kg).
  G5. multiccd is ALREADY ON at robosuite assembly (robocasa kitchen.py
      enable_multiccd=True); h12_mujoco's patch is a no-op. Audit's multiccd
      causal story is wrong. Solver is already Newton too.
  G6. Air: robosuite base.xml gives the world density=1.2 viscosity=2e-5 (air
      drag); the twin is vacuum (MuJoCo default). Small forces, exact-parity
      item.
  G7. Safety layer is a functional pass-through for stand-magnitude commands
      (kp<=200<500, kd<=5<30, dq=0, tau_ff clipped only above 0.6x URDF - knee
      180 Nm, ankle-pitch 36 Nm). Two kill modes to WATCH, not fix: a latched
      estop from one bad lowstate sample (grep 'estop_triggered'), and the
      controller-side stale watchdog (yaml stale_sec 1.5 - ok). It publishes
      idle kp=0 zeros at 500 Hz from launch; the sim's manual-band engagement
      latch gates on kp>1 so this is handled (harness path does NOT gate on kp
      - use the manual band + --auto-release for honest tests).
  G8. imu_pitch_offset_deg DEFAULTS to +1.6 deg (real-robot mount cal) in both
      cores; mjpc_fullbody.yaml already zeroes it. Verify it stays zeroed.
  G9. The launch docstring "pair with --twin-contact" is STALE: the sim's own
      code comments record pyramidal+impratio100 as a FAILED A/B (tilt 13->21;
      impratio is inert on pyramidal cones) and point to --elliptic-contact.
  G10. Stand target: base z=1.020 (stand_up keyframe, knee 0.35), enforced by
      one-sided Base Height cost weight 450 + Height 100 consuming the
      sportstate-reconstructed base z. Sag = these terms losing to something.

S1. dt COHERENCE - plant timestep 0.005 to match the deploy config
  (a) Hypothesis: the stand fails because the plant runs dt=0.002 while
      twin_dt/tick_dt=0.005 skew the controller phase clock 2.5x and scale
      planner-perceived base velocity to 0.4x; and the deploy chain is tuned to
      a 0.005 plant (twin T2-hangs/T3b-stands dt evidence).
  (b) Mechanism: h12_mujoco.py --sim-dt (opt.timestep override before
      SimInterface); deploy_common.cc twin-time; estimator step_dt.
  (c) Command: sim flag `--sim-dt 0.005` (yaml already at twin_dt/tick_dt
      0.005 - no ros-side change).
  (d) Predicted: bring-up phases take correct sim durations; sag delayed or
      gone; if still falls, the signature changes.
  (e) Falsify: identical sag timing/signature vs section 13.
  NOTE: this is the coherence BASELINE - include in every trial. The pure
      dt-physics ablation (plant 0.002 + twin_dt/tick_dt 0.002) can run later.
  RESULT: PENDING

S2. gravity_ff = 0 (the TWIN-BENCH value; yaml edit, not a controller change)
  (a) Hypothesis: 0.85 gravity feed-forward over-lightens the legs on a MuJoCo
      plant (the fork's own documented twin failure: "knee-strut collapse") -
      the exact vertical-sag signature of section 13.
  (b) Mechanism: tau_ff = gff * qfrc_bias(planner model, qvel=0) added to every
      joint cmd (deploy_common.cc:932-939,1062). Flag doc: REAL 0.85, TWIN 0.
  (c) Command: core_ws/src/h1_bringup/config/mjpc_fullbody.yaml ->
      gravity_ff: 0.0 (symlink-installed; no rebuild needed).
  (d) Predicted: knee-buckle sag stops; policy carries weight through PD; band
      goes/stays slack post-release.
  (e) Falsify: sag persists with same rate; or robot now tips instead (would
      indicate the plant needs partial ff - bracket 0.4).
  SCOPE NOTE: this is bench deployment config (per-plant by design), NOT a
      retune of shared controller gains/weights.
  RESULT: ⚠️ T2 (full parity + gff=0): STILL FELL AT RELEASE, but the failure
      moved and the bring-up got much cleaner (tilt 0.7-3.7 deg vs 5+ deg,
      assist 4-20 Nm vs 28-33). New signature: perfect scripted phases, then
      LATERAL CoM drift starting exactly at policy-blend end (engaged+13 s;
      node lean lat -4.9 -> -29.7 deg, trueXY y -0.67 m) with the one-knee-
      strut (knee 0.73/0.17) - the audit's documented lateral-drift collapse,
      now under PLANNER control. gff=0 is likely necessary but not sufficient;
      the planner's closed loop is unstable on this plant -> S6/S4-variant/S7.

S3. TRUTH base state consumed by the controller

  (b) Mechanism: sim --truth-sportstate publishes IMU-site world pos/linvel on

      currently reads rt/sportmodestate_est (estimator). NOTE deploy_common
      overwrites the VELOCITY with its own finite-diff; the position stream
      (xy + height) is what matters (Base Height weight 450).
  (c) Command: sim flag `--truth-sportstate` + yaml sportstate_topic:
      rt/sportmodestate (estimator stays parked on _est for side-by-side).
  (d) Predicted: estimator-vs-truth divergence visible ([manual] trueXY vs
      estimator xy log); with truth the stand holds or fails differently.
  (e) Falsify: truth-fed run sags identically -> state source is not the gap.
  RESULT: PENDING

S6. BASE SKY-HOOK PARITY - free-joint damping 10 / armature 0.1  [NEW - not in audit]

      sky-hook is not the (dominant) gap at stand velocities.

S15. SPAWN-FRAME STATE - publish DDS state in the robot's home frame  [NEW]
  (a) Hypothesis: RoboCasa is the ONLY plant that hands the controller raw
      kitchen-world pose (xy ~(-2.2,-3.6), arbitrary spawn yaw). The twin
      spawns at the model origin facing +x; the real IMU boots at yaw ~0 with
      odometry from 0. The Lean task's Body Yaw cost (weight 40, lean.cc:2135)
      aligns the torso's forward xy with reach_dir = direction from the torso
      to reach_target = object_pos -- the PHANTOM OBJECT inside the planner
      model at ~(1.1, 0). A yaw'd/offset robot therefore carries a permanent
      weight-40 heading error it can only reduce by pivoting itself -- the
      persistent lateral drift + one-knee-strut fold seen in T1/T2/T3 AND
      (via the raw lowstate quaternion, which the estimator chain passes
      through too) in every section-13 trial.
  (b) Mechanism: new flag --spawn-frame-state (added this session):
      unitree_interface publishes the lowstate IMU quaternion with the spawn
      yaw rotated out, and the truth sportmodestate position spawn-relative
      (xy from ~0, z referenced to the walking-surface top 0.02) + velocity
      yaw-derotated. Exact rigid-transform consistency with the node's
      pelvis = p - R*kImuOffset reconstruction.
  (c) Command: sim flag `--spawn-frame-state`.
  (d) Predicted: node lean/tilt telemetry no longer shows a persistent
      lateral heading error; the post-blend drift disappears; the free stand
      holds. Prediction detail: T1-T3's drift direction should correspond to
      the spawn-yaw/object-direction mismatch (check yaw0 in the log).
  (e) Falsify: identical lateral drift with spawn-frame state on.
  RESULT: ✅✅ T4 (T2 + --spawn-frame-state): THE DRIFT IS GONE. Spawn yaw was
      180.0 deg (!) - every prior kitchen trial had the planner paid w=40 to
      turn the robot fully around. Post-release: strap SLACK 0 N and stayed
      slack (first genuinely free stand), trueXY FROZEN at (-2.35,-3.31)
      (zero drift), z 0.96-0.97 for ~20 s. Remaining failure: a growing tilt
      OSCILLATION (2->9->16->31->66 deg over ~20 s, ~2-3 s swings) -> fell at
      t=55.6. The yaw/frame poison was the drift; an under-damped tilt limit
      cycle is what's left -> S16.

  (c) Command: sim flag `--foot-solref 0.02` (or --soft-feet to drop the

  (d) Predicted: tilt oscillation envelope stops growing; free stand holds

  (e) Falsify: same oscillation at 0.02 -> suspect planner-vs-plant cone
